
Client integration guide — long streaming, retries, connection pools
Aimed at any client integrating with the chinzy relay over a long-running streaming endpoint (deepseek-v4-pro thinking mode, claude-sonnet-4.5 with extended thinking, gpt-5-pro reasoning, etc.). Covers the failure modes we've seen in production and the recommended client config.

TL;DR — recommended httpx config
import httpx

client = httpx.Client(
    base_url="https://chinzy.com",
    timeout=httpx.Timeout(connect=5.0, read=120.0, write=10.0, pool=5.0),
    limits=httpx.Limits(max_keepalive_connections=0),
    transport=httpx.HTTPTransport(retries=1),
)
Equivalent settings exist for aiohttp, requests, and the OpenAI / Anthropic SDKs (which both wrap httpx internally and honor the same timeout shape).

Server-side guarantees (as of PR #27 / 2026-05-11)
The relay emits an SSE keep-alive comment (: keepalive\n\n) every 15 seconds on every streaming endpoint. This is invisible to SSE-spec-compliant parsers and resets any read-timer in the path, including:

httpx read_timeout (per-chunk, not per-request)
NAT / middlebox idle-session timers
Caddy HTTP/2 idle stream timers
Any corporate / ISP HTTP proxy that resets idle streams
Net effect: as long as your client trusts our SSE stream, you should NEVER hit a read timeout during a long generation, even when the upstream model is silent for 30-60s mid-thinking.

Failure modes we've seen and the recommended client mitigation
1. httpx.ReadTimeout mid-stream during long thinking
Symptom: client gets ReadTimeout after exactly N seconds where N = your read timeout.

Server-side fix: PR #27 (deployed 2026-05-11) emits keep-alive comments every 15s.

Client-side recommendation: set a generous read=120.0 anyway, because individual reasoning tokens can be ~5KB each and slow-start TCP plus a brief upstream pause can occasionally push gap-between-chunks above the default 60s.

2. httpx.ConnectError on the FOLLOWING request
Symptom: a streaming request finishes cleanly (status 200, full payload), but the very next request from the same client throws ConnectError. Especially common when calls are 1+ minute apart.

Root cause: httpx's connection pool retains the TCP socket for reuse. Between requests, something kills that socket silently:

A middlebox (NAT, corporate proxy, ISP) closes idle TCP sessions after 60-300s.
The server-side keep-alive timer fires (server.keepAliveTimeout = 75s in our case).
The OS drops the half-closed connection.
When the client tries to write the next request to the stale socket, it gets ECONNRESET / ConnectError. The first write fails before any HTTP-layer handshake.

Pick one of these mitigations:

Option	When	Tradeoff
limits=Limits(max_keepalive_connections=0)	Always safe	~50ms extra per request for TLS handshake
transport=HTTPTransport(retries=1)	Burst-y traffic	One implicit retry on connection errors only
Wrap call in try/except + manual retry	Custom control	Most code, most flexibility
For an LLM workload where calls are 5-30s each, the ~50ms TLS overhead of disabling pool reuse is completely irrelevant — and it eliminates an entire class of "intermittent failures every few minutes" bugs.

3. The 60s request aborted pattern
Symptom: caddy logs show status: 0, duration: 59.83, size: 0 repeatedly. Client sees RemoteProtocolError or BadRequestError: request aborted.

Root cause: client requested stream: false, upstream model takes > 60s, client's read_timeout=60 kills the connection before the relay can flush the response.

Fix: use stream: True. Once first-byte arrives within a few seconds, the read_timeout is reset on every chunk thereafter (and our keepalives ensure chunks keep flowing).

Already deployed: PR #16 ships actual SSE streaming pass-through; PR #27 adds the keep-alive layer. Combined, the 60s abort pattern should be impossible if you set stream=True.

OpenAI SDK config
from openai import OpenAI
import httpx

client = OpenAI(
    base_url="https://chinzy.com/v1",
    api_key="<your-chinzy-key>",
    http_client=httpx.Client(
        timeout=httpx.Timeout(connect=5.0, read=120.0, write=10.0, pool=5.0),
        limits=httpx.Limits(max_keepalive_connections=0),
    ),
    max_retries=2,
)

resp = client.chat.completions.create(
    model="deepseek-v4-pro",
    messages=[...],
    stream=True,          # always for long-thinking models
)
for chunk in resp:
    ...
Anthropic SDK config
from anthropic import Anthropic
import httpx

client = Anthropic(
    base_url="https://chinzy.com/anthropic",
    api_key="<your-chinzy-key>",
    http_client=httpx.Client(
        timeout=httpx.Timeout(connect=5.0, read=120.0, write=10.0, pool=5.0),
        limits=httpx.Limits(max_keepalive_connections=0),
    ),
    max_retries=2,
)

with client.messages.stream(
    model="deepseek-v4-pro",                         # cross-protocol OK
    max_tokens=8000,
    messages=[{"role": "user", "content": "..."}],
) as stream:
    for text in stream.text_stream:
        ...
Note: with PR #24 you can put ANY model alias in the Anthropic endpoint (deepseek-v4-pro, gpt-5.1, gemini-3-pro-preview, etc.). The relay handles cross-protocol translation transparently.

Cross-protocol behavior
Client SDK	Model alias	Path
OpenAI Python	deepseek-v4-pro	OAI passthrough
OpenAI Python	claude-sonnet-4.5	PR #20 OAI → Anthropic adapter
Anthropic Python	claude-sonnet-4.5	Anthropic passthrough
Anthropic Python	deepseek-v4-pro	PR #24 Anthropic → OAI adapter
All four paths emit the same SSE keep-alive heartbeat. Cross-protocol responses are translated chunk-by-chunk so client SDKs see the format they expect.

DeepSeek thinking-mode notes
If you use OAI SDK with deepseek-v4-pro, the relay (PR #21) merges DeepSeek's separate reasoning_content field into content wrapped in <think>...</think> tags so you can render the chain-of-thought inline. Multi-turn conversations work transparently — PR #22 / #23 handle the round-trip of the field automatically; you don't need to preserve or strip the tags on your side.

Server-side observability (for debugging)
When you report "still erroring", we can correlate via:

-- last hour of failed requests, with upstream error body
SELECT "createdAt", "publicModel", "platformStatus",
       LEFT("providerErrorBody", 400)
FROM "RequestLog"
WHERE "createdAt" > NOW() - INTERVAL '1 hour'
  AND "platformStatus" >= 400
ORDER BY "createdAt" DESC;
If you can include your client-side error timestamp (precise to the minute), we can pull the exact request from caddy logs and trace it through the api logs.
