# DeskPet 安装包瘦身评估（WI-10）

**日期**: 2026-05-22
**性质**: 评估文档（不是实现方案）
**目标**: 把当前约 5.4 GB 的 MSI 降到 **< 800 MB**（理想 < 500 MB）

---

## 1. 问题陈述

当前内测 MSI 约 **5.4 GB**，并且由于 Windows Installer 会把安装包缓存一份到
`C:\Windows\Installer\`，**安装时 C 盘还要额外腾约 7 GB**（见《已知问题》#1）。

对一个「桌面宠物」类应用，5.4 GB 的下载量 + 7 GB 的磁盘门槛是**严重的安装转化
杀手**——用户预期一个桌宠是几十到几百 MB 级别的东西。这是内测放量前必须正视的
体验问题。

---

## 2. 体积构成分析

5.4 GB 的 MSI，绝大部分体积来自**打包进去的 Python 依赖和本地 AI 模型权重**。

### 大头依赖（来自 `backend/pyproject.toml`）

| 依赖 | 用途 | 量级 |
|---|---|---|
| `torch>=2.6,<3`（CUDA wheel） | BGE-M3 / 部分模型的张量后端 | **最大单项**，CUDA 版 torch 含 cuDNN/cuBLAS 等，单独就是 GB 级 |
| `FlagEmbedding` + `transformers` + `peft` | BGE-M3 嵌入模型的运行框架 | 数百 MB（含 transformers 一大堆） |
| `browser-use` + `playwright` 相关 | code-mode 的浏览器自动化（`[code_e2e]` 用） | 框架本身不大，但 chromium 浏览器内核很大——注：chromium 是**首次运行才下载**，不打进 MSI |
| `silero-vad` | 语音活动检测，JIT 模型随包 | 中等（JIT 模型几十 MB） |
| `mss` / `pyautogui` / `prometheus-client` / `mcp` 等 | 各类工具 | 小，可忽略 |

### 本地 AI 模型权重（最大头）

模型权重通过 `paths.resolve_model_dir()` 解析，frozen 构建里打在
`sys._MEIPASS/models/` 下。涉及的模型：

| 模型 | 子目录 | 体积（约） | 当前是否进 MSI |
|---|---|---|---|
| BGE-M3（INT8 量化） | `bge-m3-int8/` | **~286 MB** | 是 |
| faster-whisper large-v3-turbo | `faster-whisper-large-v3-turbo/` | 数百 MB～1 GB 级 | 是 |
| CosyVoice2（TTS） | `cosyvoice2/` | GB 级（CosyVoice 模型较大） | 是 |
| BGE-reranker-v2-m3 | （memory-v2 reranker 用） | ~127 MB | 视构建而定 |
| silero VAD | `silero_vad/`（随 pip 包） | 几十 MB | 是 |

**初步判断**：5.4 GB 里，**CUDA 版 torch + 三个大模型（whisper / cosyvoice /
bge-m3）合计就占了绝大多数**。这正是瘦身的主战场。

> 准确的逐项体积需要在一次真实构建后用 `du` / 资源管理器逐目录量取——
> 本文给出的是基于依赖清单的量级估计，供决策用。

---

## 3. 瘦身可行性评估

### 3.1 把大模型移出 MSI、改首次启动按需下载 —— ✅ 强烈推荐

**思路**：MSI 只装程序本体 + 运行时框架，**不打模型权重**。模型在首次启动
（或首次用到该能力）时从网络按需下载到用户的 `models/` 目录。

**可行性**：高。代码侧已经为此留好了路：

- `paths.resolve_model_dir()` 已经是多源 fallback——优先查 `user_models_dir()`，
  没有才退回 bundle。模型不在 MSI 里时，下载到 `user_models_dir()` 即可被找到。
- 代码已有「模型缺失时降级」的设计：faster-whisper 缺失会回退 HuggingFace
  自动下载，BGE-M3 缺失会回退 mock 向量。也就是说**模型不在包里不会让程序起不来**，
  只是相应能力降级——这正是按需下载方案需要的兜底语义。

**收益**：把 whisper + cosyvoice + bge-m3 三个大模型移出，MSI 体积有望从
5.4 GB 砍到接近目标区间。具体能否进 800 MB 还取决于 torch 的处理（见 3.2）。

### 3.2 CUDA 版 torch —— ⚠️ 需单独决策

torch 的 CUDA wheel 是另一个 GB 级大头。它**不是模型权重，是运行时**，
没法像模型那样「按需下载」得那么自然。可选路径：

- **A. 改用 CPU 版 torch**：体积小很多，但 BGE-M3 / reranker 在 CPU 上慢。
  对一个桌宠的记忆召回场景，CPU 推理的延迟**可能可以接受**——需要实测。
- **B. torch 也做按需下载**：把 torch 相关的大体积部分（CUDA 库）做成可选
  组件，首启动时按用户有无 GPU 决定下载 CPU 版或 CUDA 版。工程上更复杂。
- **C. 评估能否完全不依赖 torch**：BGE-M3 是否有 ONNX / 纯 C++ 推理后端
  （如通过 onnxruntime）可以替代 FlagEmbedding+torch 这条重链路。这是最彻底
  但也最大的改动。

**建议**：内测期先走 3.1（移模型），torch 处理留作下一步深入评估。仅移模型
能否达标先实测，不够再动 torch。

### 3.3 已经做对的部分

- `playwright` 的 **chromium 浏览器内核已经是首次运行才下载**，不打进 MSI
  （见 `pyproject.toml` 注释：「chromium downloads lazily on first real run」）。
  这是按需下载模式的一个已落地的先例，证明这条路在本项目里走得通。

## 4. 「模型按需下载」技术方案要点

如果决定实施 3.1，下载器需要满足：

### 4.1 进度可见

- 首次启动检测到模型缺失 → 弹出明确的下载界面，**显示进度条**（百分比 + 速度
  + 预计剩余时间）。
- 下载期间**不阻塞**应用启动——桌宠先出来，相应能力（记忆 / 语音）暂时降级，
  下载完成后自动切回真实模型。这与现有「模型缺失则降级 mock」的语义一致。

### 4.2 断点续传

- 大文件（whisper / cosyvoice 都是几百 MB～GB 级）下载必须支持**断点续传**
  （HTTP Range 请求）。内测用户网络环境参差，一次性下完不现实。
- 中途退出 / 断网 → 下次启动从断点继续，不从头来。

### 4.3 完整性校验

- 每个模型文件附带 **sha256 校验值**。下载完成后校验，不匹配则判为损坏 →
  自动重下。
- 校验值随程序内置（或随版本清单下发），防止下载到被篡改/损坏的权重。

### 4.4 下载源

- 候选：GitHub Release assets（和安装包同源，管理简单）、对象存储（CDN 加速，
  国内用户体验更好）。
- 内测期可先用 GitHub Release assets（零额外基础设施）；若国内下载速度成为
  反馈热点，再评估对象存储 / 镜像。
- 下载源地址应可配置 / 可切换，便于将来加镜像。

### 4.5 失败兜底

- 下载彻底失败（多次重试无果）→ 不让应用变砖：相应能力维持降级态
  （记忆走 mock、TTS 走在线 edge-tts），并给用户明确提示「X 模型下载失败，
  可稍后在设置里重试」。

---

## 5. 结论与建议

| 项 | 评估 | 建议 |
|---|---|---|
| 移除 whisper / cosyvoice / bge-m3 三大模型 | 可行性高，代码已留好降级与多源解析 | **优先做**，预期能砍掉绝大部分体积 |
| CUDA 版 torch | 是第二大头，处理较复杂 | 移模型后实测体积，不达标再单独评估（CPU 版 / ONNX） |
| 模型按需下载器 | 需新增功能，要点见第 4 节 | 配套 3.1 一起做 |
| chromium | 已经是按需下载 | 无需改动，可作为方案参照 |

**底线判断**：MSI < 800 MB 的目标，**仅靠移除三个大模型很可能就能达成或接近**；
能否进 500 MB 取决于 torch 的处理。建议把本项拆成两步——先移模型（收益大、
风险低、代码已支持），再视实测结果决定是否动 torch。

> 重申：本文是**评估**。实际实施需要单独的 spec / OpenSpec change，包含下载器的
> 详细设计、UI、测试计划，以及一次真实构建后的逐项体积测量来校准估计。
