## What this proves

### 1. ✅ Hard Gate's `HALLUCINATION_DETECTED` fires in real life

The first auto_resume event used **`reason=hallucination`** — that's the
TerminationReason enum value from P6's `TerminationGate.allows_tool()` when
`state.per_tool_consecutive[name] >= per_tool_max_consecutive` (default 5).

This is the **new code path from Phase 1**. Pre-P6, this protection didn't
exist — the agent would simply keep ignoring soft `_TOOL_BUDGET_HARD_MSG`
system messages and keep tool_using until max_iterations or a real error.

### 2. ✅ AutoResume orchestrator hooks into Gate's ErrorEvent

The Phase 5 integration test (`test_long_task_breaks_with_tool_budget_reason`)
asserted the gate yields ErrorEvent with `reason='error_tool_budget'`.

In production we observed `reason='hallucination'` (different but symmetric
gate exit). The AutoResume orchestrator successfully consumed this
ErrorEvent and spawned a recovery turn — **the integration between Gate
and AutoResume is real and end-to-end working.**

### 3. ✅ B1 tool_result truncator (ContextManager) working

Multiple `p5s2_tool_result_truncated` lines: 62255 → 2085, 19675 → 2085,
7756 → 2084, etc. Long `read_file` outputs are being collapsed to 2KB
keepers + ref_id, which is exactly what `ContextManager.record_tool_result`
should do for non-`fetch_tool_result` tools.

### 4. ✅ Coexistence with supervisor + max_iter rescue (no regression)

After Phase 1's hard gate fires (`reason=hallucination`), the LEGACY
`supervisor_max_iter_rescue` path STILL works (`reason=max_iterations`
attempt=2). P6 didn't break the existing rescue mechanism — it added a
new, earlier safety layer on top.

### 5. ✅ Multi-attempt auto-resume bounded

`max_attempts=2` config (from [supervisor]) was respected. After attempt=2
runs out, the session terminates without infinite recursion.

## Anti-evidence (negative result)

- We did NOT observe `error_tool_budget` (40-tool cap not hit in this run)
  because the hallucination cap (5 consecutive same-tool calls) fired first.
  That's correct — the Gate uses whichever cap trips first.
- We did NOT observe `error_wall_clock_exceeded` (600s cap not hit) because
  hallucination/max_iter caught things much earlier. Wall-clock is the
  "ultimate safety net" — good that it's never exercised in normal runs.
