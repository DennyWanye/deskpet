## Observation

### Orchestrator decision tree (verified by tests)

| Trigger reason | enabled | attempts<max | supervisor returns | result |
|---|---|---|---|---|
| max_iterations | true | yes | nudge+hint | spawned, attempt+1 |
| circuit_open | true | yes | nudge+hint | spawned, snapshot includes circuit detail |
| permanent_tool_error | true | yes | nudge+hint | spawned |
| any | true | yes | ask_user | ask_user, attempts unchanged |
| any | true | NO (≥max) | (not called) | exhausted, ws event emitted |
| any | **false** | n/a | (not called) | ask_user, reason="disabled" |

### Audit row shape (production)

Each spawn calls `_auto_resume_audit({...})` which writes via
`SessionDB.append_supervisor_hint(action='auto_resumed', ...)` with:
- `session_id` = original sid
- `alert_id` = supervisor's alert_id (from SupervisorAction)
- `hint_text` = the supervisor's `hint_for_main_agent`
- `severity` = supervisor's severity
- `diagnosis` = supervisor's diagnosis string

Inspectable via:
```sql
SELECT * FROM supervisor_hints WHERE action='auto_resumed' ORDER BY ts DESC;
```

### main.py wiring decisions

The trickiest design call: how does the orchestrator spawn a fresh chat
task when `_run_chat` is closured inside the chat handler's
`if msg_type in ("chat","chat_v2")` branch (~700 lines, no easy
extraction)?

**Chosen approach**: a per-sid `_auto_resume_redispatchers: dict[str,
Callable]` populated by the chat handler each user turn. Production
dispatcher trampoline:

1. Orchestrator passes `(sid, msgs)` where `msgs` ends in a
   `_is_supervisor_hint=True` system msg
2. Trampoline extracts hint text and pushes a `Hint` to `nudge_queue`
   (uniform with how P5-S1 supervisor injects hints — at next chat
   handler entry, `pop_all` puts it at top of system stack)
3. Trampoline calls the per-sid re-dispatcher with synthetic trigger
   text `<<auto_resume>>` (matches the existing `<<supervisor_followup>>`
   pattern at line 2702)
4. Re-dispatcher creates a fresh `_run_chat` task, registers it in
   `_chat_inflight`, attaches the followup_cb so any further hints are
   chained

Rationale: this avoids the 700-line `_run_chat` extraction the spec
warned against (tasks.md 4.10 explicitly allowed simplification). The
trade-off: production wiring uses nudge_queue as the injection medium
rather than passing `_msgs` directly through. Unit tests verify the
orchestrator-side contract (hint IS in `disp.calls[0][1]`); the
trampoline implementation is a black box from the test's perspective —
it satisfies the contract and routes through the existing P5-S1 plumbing.

The synthetic trigger `<<auto_resume>>` is also why the user-message
counter-reset at chat handler entry is gated by `not text.startswith("<<")`
— synthetic re-entries should consume the existing budget, not get a
free new one.

### `auto_resume_succeeded` ownership

Per spec: "由 main.py 在新 task FinalEvent 时 emit, NOT orchestrator".
Implemented in `main.py` `_FinEv` branch:

```python
sa = await session_activity.get(sid)
if sa.auto_resume_attempts > 0:
    await ws.send_json({
        "type": "auto_resume_succeeded",
        "payload": {"session_id": sid, "attempts": sa.auto_resume_attempts},
    })
```

The counter is **not** reset on success — only on a fresh user message.
This matches spec scenario "User new message resets the attempt counter".
