# Evidence: 3.16 — Phase 3 chain + resolution tests green

**Date**: 2026-05-11
**Phase**: Phase 3 — AgentLoop chain + per-session resolution
**Tasks covered**: 3.1–3.15 (12 tests + 2 impl files)

## Summary

Phase 3 delivers:

1. **AgentLoop chain walking** — new `provider_chain` parameter on
   `AgentLoop.run()`. When supplied, the loop calls each provider's
   `chat_with_tools()` in order, falling back on transient
   `LLMProviderError` and emitting a `ProviderChainFallbackEvent`
   diagnostic event. On exhausted chain → `ErrorEvent(reason=
   "all_providers_failed")`; on empty chain → `ErrorEvent(reason=
   "no_provider_configured")`.

2. **Per-session resolution** — new `backend/llm/resolution.py` with
   `resolve_provider_for_session(base_sid, *, is_code_session,
   registry, session_db)`. Implements the 5-step algorithm in the
   `code-session-provider-binding` spec (companion skip → DB lookup →
   pinned single chain → stale binding fallback → global chain with
   optional model override).

3. **Backwards compat** — pre-Phase-3 callers that pass a single LLM
   registry (legacy `chat_with_fallback` path) keep working unchanged.
   `provider_chain` defaults to `None`; the loop falls through to the
   old call site.

4. **Error taxonomy extension** — `tool_call_args_malformed_json`
   added to `PERMANENT_KEYWORDS` so an LLM emitting structurally broken
   JSON args breaks out of the loop rather than spinning. Same args
   would always parse-fail identically — keeping a dispatch loop alive
   is wasted budget.
