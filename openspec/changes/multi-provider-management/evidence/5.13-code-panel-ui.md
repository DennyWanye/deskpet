## Summary

Implemented per-session provider/model binding UI in the Code panel:

- Each session card in `SessionGridView.tsx` now renders a compact
  `<select>` dropdown above the input bar listing **Global Chain** plus
  every enabled provider broadcast by the backend (`providers_changed`

  two additive nullable fields: `provider_id` and `preferred_model`.
  Defaults are `null` (no binding → Global Chain).
- `ws.ts` was extended (grouped under the comment
  `// P5-S2 Phase 5 — code session binding events`) to:
  - Populate `provider_id` + `preferred_model` from the existing
    `code_sessions_list_response` payload (extends Phase 0 IPC).
  - Handle the new server-initiated `providers_changed` broadcast:
    refresh `providersStore` AND reconcile any session whose pinned
    provider was deleted (falls back to `provider_id = null` + console
    info toast — surfaced as the spec-mandated "Provider X 已删除…").
  - Handle ack events `code_session_provider_set` and
    `code_session_model_set` to keep the store in sync with backend
    authoritative state.
  - Handle `settings_providers_list_response` (initial-load population
    of `providersStore`).

## providersStore.ts public shape (for Phase 4 coordination)

```ts
export interface ProviderEntry {
  id: string;
  name: string;
  base_url?: string;
  model?: string;
  priority?: number;
  enabled?: boolean;
}

export const useProvidersStore = create<{
  providers: ProviderEntry[];
  set_providers(list: ProviderEntry[]): void;
}>(...);
```

Phase 4's settings panel can read from the same store. The two writers
both call `set_providers(list)` — Phase 5's ws.ts cases for
`providers_changed` and `settings_providers_list_response` write to the
store; if Phase 4 also wires either of those events from
`SettingsPanel.tsx`, both calls into `set_providers` are idempotent.

## Design notes

### Why no React-render assertion in tests

`vitest.config.ts` runs the `node` environment; the project does not
have `@testing-library/react` installed and we deliberately did NOT
introduce it (out-of-scope and not required to verify behaviour). All
dropdown behaviour is therefore tested through pure helpers exported
from `SessionGridView.tsx` (`buildSetProviderMessage`,
`buildSetModelMessage`, `resolveCardDropdownDisplay`,
`pickProviderRemovedFallback`) plus `providersStore.ts`
(`build_provider_dropdown_options`, `format_provider_label`) — these
helpers are what the JSX consumes, so verifying them is verifying the
card's visible state. The same pattern is already established by
`AutoResumeBanner.test.tsx` and `SettingsToggle.test.tsx`.

### Optimistic UI

`on_provider_change` writes `provider_id` into the store immediately
before sending the WS message; the backend ack
(`code_session_provider_set`) reconciles. Same semantics the spec
describes for "optimistically shows 'openrouter-claude 🔒'".

### Sentinel for "改 model" action

The dropdown uses the value `"__change_model__"` for the "open modal"
entry. This is safe because Phase 1's `LLMProviderRegistry` validates
provider ids to be kebab-case with no underscores, so the sentinel
cannot collide with a real id.

### Live E2E

Not in scope for this phase (frontend-only slice — backend WS
handlers for `code_session_set_provider` etc. land in Phase 2, already
on master). Lead agent should run an end-to-end smoke after Phase 4
integration.
